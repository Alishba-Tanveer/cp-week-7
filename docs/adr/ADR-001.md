# ADR-001: Use Offset Pagination for List Endpoints

**Status:** Accepted

**Date:** 2026-09-04

## Context

The Task Management Platform is a NestJS REST API backed by PostgreSQL and TypeORM. The fixed business domain contains the seven Week 5/6 tables:

* `users`
* `projects`
* `project_members`
* `tasks`
* `tags`
* `task_tags`
* `comments`

The API contains list endpoints that may return many records, particularly for tasks, projects, comments, and other collections. Pagination is therefore required so that a request does not need to return an unbounded number of records.

Several forces affect the pagination design:

1. **Existing API interface:** The REST API contract is page-oriented and defines `page` and `pageSize` query parameters for paginated collection endpoints.

2. **Current application scale:** The Task Management Platform is an internship-scale application with a moderate expected dataset rather than a high-volume feed containing millions of rapidly changing records.

3. **Client usability:** API consumers need a simple way to request a particular page and page size without having to store or understand an opaque cursor.

4. **Random page navigation:** A page-based interface can directly request a specific page, such as page 1, page 2, or page 5.

5. **Implementation complexity:** The pagination approach should work naturally with the existing TypeORM repository/query patterns and should not introduce unnecessary API or database complexity.

6. **Changing data:** Tasks, comments, and other records can be inserted, updated, or deleted while clients are navigating through pages, so pagination behavior must be understood in the presence of data changes.

7. **Future scalability:** The chosen approach should remain suitable for the current application while leaving a clear point at which a different pagination strategy could be introduced if the data volume or access pattern changes significantly.

## Options Considered

### Option 1: Offset Pagination

Under this approach, collection endpoints use `page` and `pageSize`. The requested page is translated into a database offset and limit.

For example:

* `page=1&pageSize=20` requests the first 20 records.
* `page=2&pageSize=20` requests the next 20 records.

The API can return pagination metadata such as the current page, page size, total count, and total pages.

**Advantages:**

* Matches the existing Week 7 REST API contract using `page` and `pageSize`.
* Simple for API consumers to understand and implement.
* Supports direct navigation to a particular page.
* Fits naturally with TypeORM's `skip` and `take` pagination approach used during Week 6.
* Makes total-count and total-page metadata straightforward to expose.
* Appropriate for the current moderate-sized Task Management Platform.

**Disadvantages:**

* Large offsets can become less efficient as the dataset grows.
* Inserts or deletes between requests can cause records to shift between pages.
* A client navigating through multiple pages may see duplicates or miss records if the underlying dataset changes between requests.
* Performance may degrade for very deep pages on sufficiently large datasets.

### Option 2: Cursor Pagination

Under this approach, the API returns a cursor representing the position of the last record in the current result set. The client supplies that cursor to retrieve the next set of records.

For example, an endpoint could return a `nextCursor` and the client could use that cursor to request the next page.

**Advantages:**

* Performs better than large offsets for very large datasets when the cursor uses an appropriate indexed ordering column.
* More suitable for continuously changing or high-volume collections.
* Can provide more stable traversal through a result set when records are inserted or deleted.
* Avoids repeatedly scanning or skipping a large number of preceding records for deep pages.

**Disadvantages:**

* More complex for both the API implementation and API consumers.
* Requires cursor generation, validation, and decoding/encoding rules.
* Does not naturally support jumping directly to an arbitrary page such as page 10.
* Would require changes to the existing `page` and `pageSize` API contract.
* Requires a carefully defined and consistently indexed ordering strategy.
* Total-page calculations are less natural than with offset pagination.

## Decision Criterion

The primary decision criterion is **the best balance between compatibility with the existing API contract, client simplicity, and the current scale of the Task Management Platform**.

Because the current API is already page-oriented and the application's expected dataset is moderate, the simplicity and compatibility of offset pagination provide greater value at this stage than the scalability benefits of cursor pagination.

## Decision

**We will use offset pagination for the Task Management Platform's paginated list endpoints.**

Paginated endpoints will use the existing `page` and `pageSize` query parameters defined by the REST API contract.

The pagination implementation will:

* Treat `page` as a 1-based page number.
* Apply the requested `pageSize` to limit the number of returned records.
* Enforce the maximum `pageSize` defined by the API contract.
* Calculate the database offset from the requested page and page size.
* Use deterministic ordering for paginated queries so that records have a predictable position within the result set.
* Return the pagination metadata defined by the API contract where applicable.

For TypeORM queries, the implementation may use `skip` and `take` for offset/limit pagination, consistent with the pagination work completed during Week 6.

Cursor pagination will not be introduced at this stage because it would require a different API contract and additional implementation complexity that is not justified by the current application's scale and access patterns.

This decision applies to normal paginated collection endpoints. It does not prevent a future endpoint from using a different strategy if its access pattern or scale makes offset pagination inappropriate.

## Consequences

### Positive Consequences

* The pagination implementation remains consistent with the existing REST API contract.
* API consumers can use the familiar `page` and `pageSize` parameters.
* Clients can directly request specific pages.
* The approach fits naturally with the TypeORM repository/query patterns already used in the project.
* Pagination is straightforward to test and document.
* The implementation avoids introducing cursor-generation and cursor-validation logic while the application remains at its current scale.
* The team can use total-count and total-page information where required by the API contract.

### Negative Consequences

* Deep pages may become slower as the number of records grows because the database must handle increasingly large offsets.
* Changes to the underlying data between page requests can cause records to move between pages, which can result in duplicates or missed records during traversal.
* Offset pagination may eventually become unsuitable for very large or high-write collections.
* If the system later needs cursor pagination, the API contract and client behavior may need to change.

The team accepts these limitations because the current application's expected scale, page-oriented API contract, and client simplicity make offset pagination the more appropriate choice at this stage.

## Relationship to DESIGN.md and API Contract

This decision is consistent with the Week 7 system design and REST API contract.

The system uses NestJS, PostgreSQL, and TypeORM, and the fixed business domain remains:

* `users`
* `projects`
* `project_members`
* `tasks`
* `tags`
* `task_tags`
* `comments`

The pagination decision does not introduce or remove any domain entities or database tables.

The API contract uses `page` and `pageSize` for paginated collection endpoints. This ADR therefore selects the pagination strategy that directly supports those existing query parameters rather than replacing them with cursor-specific parameters.

The decision also remains consistent with the Week 6 TypeORM pagination implementation, where pagination is implemented using `skip`, `take`, and `getManyAndCount()`.

No endpoint path, entity name, table name, query-parameter name, or role name is changed by this ADR.

## Expiry / Reconsideration Condition

This decision should be reconsidered if the Task Management Platform develops a collection endpoint where **either of the following becomes true:**

1. The relevant collection grows to approximately **1 million or more records**, and measurements show that normal paginated requests—particularly deep pages—are experiencing unacceptable database latency; or
2. The application introduces a high-frequency feed or another use case where records are continuously inserted while clients are traversing many pages and stable sequential traversal becomes a requirement.

If either condition occurs, the team should benchmark the affected endpoint and evaluate cursor pagination using an indexed, deterministic ordering key. If cursor pagination provides a measurable improvement without unacceptable API complexity, the affected endpoint should be migrated or redesigned to use cursor-based pagination.

Until one of these conditions occurs, offset pagination remains the default strategy for the platform's normal paginated collection endpoints.

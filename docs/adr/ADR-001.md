# ADR-001: Use Database Transactions for Multi-Step Consistency

* **Status:** Accepted
* **Date:** 2026-09-04
* **Decision:** Use database transactions for operations that modify multiple related records and must succeed or fail as one atomic unit.

## Context

The Task Management Platform uses a fixed relational business domain consisting of the seven Week 5/6 tables:

* `users`
* `projects`
* `project_members`
* `tasks`
* `tags`
* `task_tags`
* `comments`

The Phase 4 backend will be implemented as a NestJS REST API using PostgreSQL and TypeORM. Several API operations modify more than one related record, so partial writes could leave the database in an invalid or inconsistent state.

The main forces affecting this decision are:

1. **Relational consistency:** Related records must remain consistent with foreign keys, ownership rules, and relationship constraints.
2. **Atomic business operations:** Operations such as project creation and task creation may require multiple database writes that should either all succeed or all be rolled back.
3. **Failure handling:** A database or validation failure during a multi-step operation must not leave partially completed data behind.
4. **API contract requirements:** The REST API explicitly requires project creation to atomically create both the project owner information and the corresponding owner membership.
5. **Maintainability:** The implementation should provide a clear and reusable way to protect multi-table write operations without introducing unnecessary distributed infrastructure.

A particularly important example is project creation. The API contract requires the authenticated user to become the project owner and requires `projects.ownerId` and the corresponding `project_members` owner row to remain consistent. If the project row were created successfully but the owner membership insert failed, the database could contain a project whose required owner membership is missing.

Task creation can also involve multiple writes. A task may be created together with associations in `task_tags`, so failure during relationship creation should not leave an incomplete task/tag state.

The same consistency principle applies to other multi-record operations such as project deletion, where deleting a project affects its memberships and tasks, and task deletion affects its task-tag relationships and comments.

## Options Considered

### Option 1: Perform database writes sequentially without an explicit transaction

Under this approach, the service would execute each database operation separately.

For example, project creation could:

1. Insert the project.
2. Insert the owner membership.
3. Return the created project.

**Advantages:**

* Simple to implement for basic CRUD operations.
* Less transaction-management code.
* Each individual database operation remains easy to understand.

**Disadvantages:**

* A failure after an earlier successful write can leave partial data.
* Project ownership and owner membership could become inconsistent.
* Multi-table operations require manual rollback logic.
* Manual rollback becomes increasingly difficult as the number of related writes grows.
* The implementation would not directly guarantee the atomic behavior required by the API contract.

### Option 2: Use database transactions for multi-step write operations

Under this approach, all related writes that represent one business operation are executed inside a single PostgreSQL transaction through TypeORM.

For example, project creation would:

1. Start a database transaction.
2. Insert the project with the authenticated user as `ownerId`.
3. Insert the corresponding `project_members` row with role `owner`.
4. Commit the transaction only if all required operations succeed.
5. Roll back the transaction if any required operation fails.

The same pattern would be used for other operations that require multiple related writes to remain atomic.

**Advantages:**

* Provides atomic all-or-nothing behavior.
* Prevents partially completed multi-table writes.
* Protects the consistency between `projects.ownerId` and the owner membership.
* Reduces the need for custom rollback logic.
* Uses PostgreSQL's transaction guarantees and fits naturally with TypeORM.
* Provides a clear boundary around business operations that must remain consistent.

**Disadvantages:**

* Adds transaction-management complexity.
* Transactions can hold database resources for longer if the application performs too much work inside them.
* Developers must ensure that every database operation belonging to the transaction uses the transaction's EntityManager/repository context.
* Transaction boundaries must be designed carefully to avoid unnecessary locking or long-running transactions.

### Decision Criterion

The primary decision criterion is **preserving database consistency and atomicity for business operations that modify multiple related records**, while keeping the solution appropriate for the PostgreSQL and TypeORM architecture defined for Phase 4.

Because the API contract requires certain multi-table operations to behave atomically, correctness and consistency take priority over the small amount of additional transaction-management complexity.

## Decision

**We will use database transactions for multi-step database operations where the related writes represent one atomic business operation.**

The NestJS service layer will define the transaction boundary, and TypeORM's transactional EntityManager will be used for all database operations that belong to that transaction.

The application will rely on PostgreSQL transactions and the existing relational constraints as the primary consistency mechanism. Foreign keys and other database constraints remain important safeguards, but they do not replace transactions when several writes must succeed or fail together.

The following operations will use transaction boundaries where multiple related writes are involved:

* **Project creation**

  * Create the project.
  * Create the authenticated user's `project_members` row with role `owner`.
  * Commit only when both writes succeed.
* **Task creation with tag associations**

  * Create the task.
  * Create its `task_tags` associations when `tagIds` are supplied.
  * Roll back the operation if a required write fails.
* **Task tag replacement during task update**

  * Update the task fields when applicable.
  * Replace the task's tag associations as one consistent operation when `tagIds` is supplied.
* **Project deletion**

  * Delete the project and its dependent records according to the defined relationship/cascade behavior as one consistent operation.
* **Other future multi-record write operations**

  * Any Phase 4 operation that requires multiple related database changes to represent one business action will use the same transactional approach.

Transactions will contain only the database work necessary for the atomic operation. External calls or unrelated long-running work will not be placed inside a database transaction.

This decision does not introduce distributed transactions, event-driven eventual consistency, or a separate synchronization mechanism because the current system uses one PostgreSQL database as the authoritative relational data store.

## Consequences

### Positive Consequences

* Multi-table business operations become atomic.
* A failed operation can be rolled back without leaving partial records.
* The required consistency between `projects.ownerId` and the owner `project_members` row is protected.
* Task and task-tag changes can remain consistent when they are part of the same operation.
* The approach fits the existing PostgreSQL + TypeORM architecture.
* Database constraints and transactions provide complementary protection against invalid relational state.
* The behavior is easier to reason about than manually compensating for partially completed writes.

### Negative Consequences

* Transaction handling adds implementation complexity compared with simple independent repository calls.
* Developers must correctly use the transaction-scoped EntityManager for every database operation inside a transaction.
* Poorly designed transactions could hold locks or database resources longer than necessary.

The team accepts this additional complexity because preventing inconsistent multi-table state is more important for this system than minimizing transaction-related code.

## Relationship to Existing Design and API Contract

This decision is consistent with the Week 7 system design because the backend uses a layered NestJS architecture with the service layer responsible for business operations and the relational database remaining the authoritative source of data.

It is also directly required by the REST API contract for project creation. The API specifies that project creation must atomically establish both the project's `ownerId` and the corresponding owner membership in `project_members`.

The decision also preserves the fixed seven-table business domain. Transactions change how related writes are executed; they do not introduce a new business table or change the existing domain relationships.

The decision therefore establishes the implementation rule:

> When one business operation requires multiple related database writes to remain consistent, those writes must execute within one database transaction.

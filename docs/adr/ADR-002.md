# ADR-002: Enforce Role-Based Access Control with Guards

**Status:** Accepted

**Date:** 2026-09-04

## Context

The Task Management Platform is a NestJS REST API containing authenticated users with different authorization requirements. The application needs to ensure that users can only perform operations permitted by their authenticated identity and role.

The system uses a layered NestJS architecture in which controllers receive HTTP requests and services contain business logic. Authentication identifies the requesting user, while authorization determines whether that user is allowed to perform a particular operation.

Several forces affect the authorization design:

1. **Security:** Authorization checks must be applied consistently so that a protected endpoint cannot accidentally be exposed because a developer forgot a role check.

2. **Centralization:** Common authorization rules should be implemented in a predictable location rather than duplicated throughout many service methods.

3. **NestJS architecture:** The backend uses NestJS, which provides guards as a framework-level mechanism for controlling whether a request can reach a route handler.

4. **Maintainability:** The project should avoid repeating identical role checks in every service method.

5. **Business-level authorization:** Some permissions depend on resource ownership or other business rules and therefore cannot be represented by a simple role check alone.

6. **Team development:** Multiple developers may add endpoints over time, so the authorization design should make security requirements visible and difficult to overlook.

## Options Considered

### Option 1: Enforce roles in every service method

Under this approach, each service method would explicitly check the authenticated user's role before performing the requested operation.

For example, a service method could verify that the current user has an appropriate role before creating, updating, or deleting a resource.

**Advantages:**

* Authorization logic can be placed close to the business operation.
* A service method can combine role checks with resource-specific business rules.
* The approach does not depend as heavily on controller-level configuration.

**Disadvantages:**

* The same role checks may be duplicated across many service methods.
* Developers can accidentally omit a required check when adding a new operation.
* Authorization becomes harder to audit because checks are distributed throughout the service layer.
* Repeated authorization logic increases maintenance cost.

### Option 2: Enforce role requirements with NestJS guards

Under this approach, role requirements are declared at the route/controller level and enforced by a NestJS authorization guard before the request reaches the handler.

A guard can inspect the authenticated user's role and the roles required by the endpoint.

**Advantages:**

* Authorization is centralized and consistently enforced at the HTTP boundary.
* Common role checks do not need to be duplicated in every service method.
* Required roles can be made visible on the protected controller/route.
* NestJS guards integrate naturally with the framework's request lifecycle.
* The approach is easier to audit and maintain as the number of endpoints grows.

**Disadvantages:**

* A guard alone cannot express every business-specific authorization rule.
* Resource ownership checks may still need to be performed in the service layer.
* Developers must correctly configure protected routes and required roles.
* Authorization behavior can become harder to understand if the project creates too many specialized guards or decorators.

## Decision Criterion

The primary decision criterion is **consistent enforcement of role-based access control while minimizing duplicated authorization logic**.

The platform has multiple protected REST endpoints, so a centralized mechanism is preferred for common role requirements. However, resource-specific authorization remains a responsibility of the service layer where the permission depends on the particular record being accessed.

## Decision

**We will use NestJS guards for common role-based access control at the controller/route boundary, while retaining service-level checks for resource-specific authorization and business rules.**

The authentication mechanism will establish the identity of the current user before authorization is evaluated.

For endpoints with role requirements:

1. The authenticated user identity is made available to the request.
2. The route declares the roles permitted to access the operation.
3. The authorization guard checks the user's role against the required roles.
4. Requests that do not satisfy the role requirement are rejected before the protected handler executes.
5. Services continue to perform authorization checks that depend on the specific resource, such as whether the authenticated user owns a project or has the required membership in that project.

The guard therefore handles **general role-based access**, while the service layer remains responsible for **resource-specific authorization**.

This decision does not assume that a guard can replace all authorization logic. Both layers have distinct responsibilities.

## Consequences

### Positive Consequences

* Common role requirements are enforced consistently.
* Role checks are not unnecessarily duplicated across service methods.
* Protected routes clearly communicate their required roles.
* Authorization becomes easier to audit and maintain.
* The approach fits naturally with NestJS's architecture.
* Resource-specific business rules can remain in the service layer where the necessary domain information is available.

### Negative Consequences

* Developers must correctly configure role metadata and authorization guards.
* Some authorization logic will still exist in services for ownership and membership checks.
* A guard cannot by itself determine every business-specific permission.
* The team must understand the distinction between route-level role authorization and resource-level authorization.

The team accepts this additional architectural structure because centralized role enforcement reduces the risk of inconsistent or accidentally omitted role checks.

## Relationship to DESIGN.md and API Contract

This decision is consistent with the NestJS layered architecture defined for the Task Management Platform.

The controller/guard boundary is responsible for request-level authorization, while the service layer remains responsible for business rules and resource-specific authorization.

The decision does not change the fixed seven-table domain:

* `users`
* `projects`
* `project_members`
* `tasks`
* `tags`
* `task_tags`
* `comments`

It also does not change endpoint paths, request parameters, response structures, or role names defined by the API contract.

The role names used by the authorization implementation must remain exactly aligned with the roles defined by the system design and API contract.

## Expiry / Reconsideration Condition

This decision should be reconsidered if the authorization model becomes substantially more complex than simple role-based access control—for example, if the platform introduces a requirement for fine-grained permissions based on many dynamic resource attributes, organizational policies, or an external policy engine.

If that occurs, the team should evaluate whether the current guard-based approach remains maintainable and whether a dedicated policy-based authorization mechanism is justified.

Until such a requirement exists, NestJS guards combined with service-level resource authorization remain the default authorization strategy.
